## 0. Environment mismatch (read this first)

The task brief assumed an AWS g4dn.xlarge with a Tesla T4 GPU, repo at
`~/SpecAsync-UVM`, and an ephemeral NVMe volume at `/opt/dlami/nvme/work/`.
**None of that matches this machine.** `nvidia-smi` is not installed, no
`/opt/dlami` path exists anywhere on the filesystem, and the repo actually
lives at `/home/ubuntu/Downloads/SpecAsync-UVM`. The repository content is
authentic and internally consistent (it describes work done on the real T4
instance), but this discovery task was run from a different, non-GPU machine
— almost certainly the same repo checked out on a workstation/editor host
after the experiments finished. Consequence: **there was no NVMe volume to
check in Phase 0**, and nothing was found "at risk of being lost on instance
stop" in the sense the brief anticipated. A different, related risk was found
instead — see §6.

Pre-existing uncommitted local changes were present at task start (not caused
by this task): `driver/patches/specasync_selective_apply.patch`,
`specasync_uvm_v580.95.05.patch`, and `specasync_uvm_v595.71.05.patch` are
Git-LFS-tracked; the git index holds LFS pointer stubs but the working tree
holds the real expanded patch content (LFS filters are inactive in this
shell). These were left untouched throughout, per the hard rules.

## 3. Pruned from the bundle (user decisions during staging)

Two size-driven pruning decisions were made during Phase 6, both confirmed
with you before acting:

1. **10 individually-oversized files excluded, recorded only:**
   `results/p{1,2,3,4}_d0/Stencil_OvSub/{25000,28300,32000}_20_11264/work_records.csv`
   (~12 MB each, ~115 MB total — per-work-item speculative-worker telemetry
   for the oversubscription benchmark, one file per policy × oversubscription
   size). Aggregate stats from these are preserved in
   `results/phaseB1/gate_d/stencil_ovsub/summary.txt` (staged) and
   `results/phaseB/phaseB_telemetry.csv` (staged).
2. **All `batch_records.csv` (85 MB total, git-tracked) and all remaining
   `work_records.csv` (163 MB total, untracked/gitignored) excluded from the
   bundle, recorded only.** These are raw per-fault / per-work-item ring-buffer
   dumps underlying every `timing_raw.csv` and every aggregate CSV already
   staged; at full resolution they made the bundle 251 MB (initial staging)
   against a ~50 MB guideline. `timing_raw.csv` (the actual wall-time results)
   and every cross-run aggregate were kept in full. Location for re-analysis
   if ever needed: `results/p{0-4}_d0/{6 benchmarks}/{sizes}/batch_records.csv`
   and `.../work_records.csv` in the working repository at
   `/home/ubuntu/Downloads/SpecAsync-UVM` (232 files total, all still present
   on disk — nothing was deleted from the repository itself).

Neither pruning removes any number that appears in a `.md`/`.txt` report —
every headline statistic (hit rates, wall-time deltas, cost-benefit) is
computed from these files but is also restated in the reports and/or the
small aggregate CSVs that **are** staged.

## 6. "At-risk" files — untracked/gitignored, not NVMe (see §0)

The brief anticipated risk from an ephemeral NVMe volume; that volume does not
exist on this machine. A **functionally similar but different risk** was found
instead: a nontrivial subset of the raw evidence files this task located are
**not tracked by git at all** — they exist only in this specific working
directory (`/home/ubuntu/Downloads/SpecAsync-UVM`, EBS-backed but outside git)
because `.gitignore` excludes them by name pattern. A fresh `git clone` of this
repository, on any branch, would **not** bring these along:

```
work_records.csv                              (.gitignore line matches all instances — 78 files, 163 MB)
raw_*.bin                                      (all raw ring dumps)
tests/hit_probe, tests/coalesce_probe          (probe binaries)
results/phaseB1/hit_probe/*.bin                (R11 raw evidence — GATE_A_report.md's 99.2% source data)
results/phaseB1/oracle_probe/*.bin             (R10 raw evidence — cursor before/after)
results/phaseB1/oracle_coalesce/*.bin
results/phaseB1/gate_c/*.csv                   (R10 raw evidence — STREAM interleaved timings, 5 files)
results/phaseB1/gate_d/**/*.bin, oracle_trace.bin
results/phaseB1/gate_d/**/times.csv            (R9 raw evidence — Gate D wall times, 3 files)
```

**Every one of these files is still physically present on disk right now**
(confirmed individually — none were deleted, this is a git-tracking status
finding, not a missing-file finding) and copies of the CSV/text ones were
staged into this bundle regardless of tracked status (labelled `untracked__`
in the filename prefix instead of a branch name, since they have no git
history to attribute a branch to). The `.bin` files were left in the
repository, not copied, per the bundle's CSV/report scope — their sizes and
role are recorded in §4 above.

**Recommendation:** if long-term reproducibility matters, either commit these
files (removing the relevant `.gitignore` lines) or copy them to a separate
backup outside this working directory — right now they depend entirely on
this one machine's disk staying intact.

## 7. Conflicts between branches

**None found that reflect genuine disagreement.** The history is linear
(§1), so every case of "the same filename appearing on two branches" is
simple chronological evolution, not fork divergence. Checked explicitly via
blob-hash comparison across all 5 branch tips:

- `README.md`, `benchmarks/README_benchmarks.md` — byte-identical across all
  5 branch tips (blob hash unchanged since `main`).
  Note: `README.md` still describes `driver/patches/` as a patch against
  v580.95.05 and lists v580.95.05 / kernel 6.14.x / "RTX 5070 Ti-class" as the
  reproduction target — this text was never updated for the v595/T4 port that
  all actual experimental work (Phase B onward) used. Not a branch conflict,
  but worth knowing before quoting `README.md` in the paper: `EXPERIMENTS.md`
  (also present, also staged) is the document that actually matches what was
  run.
- `EXPERIMENTS.md` — changed once, between `main` (7531 B) and
  `phaseB-v595-port` (7064 B), then unchanged through `phaseC-decomp`. The
  `phaseC-decomp` version (staged) is authoritative and newer.

One internal (same-file, cross-phase) narrative correction is worth flagging
explicitly since it could look like a contradiction if the phase reports are
read out of order: **Phase B's original headline numbers were revised twice**
by later phases, and all three versions are staged side by side in
`reports/`:
- Phase B (`SUMMARY.md`) reported STREAM "speedup" (−8.8%) and oracle
  "100× slower."
- Phase B.1 (`GATE_C_report.md`, `GATE_D_report.md`) found the STREAM result
  was host-ordering noise (reverses to +1.5–2% slowdown under interleaving)
  and the oracle result did not reproduce under controlled measurement
  (`PIPELINE_VALIDATION.md` has the side-by-side "original claim / corrected"
  table).
- Phase B.2 (`DECISION.md`) then closed the question definitively with the
  oracle-favorable C3-vs-C0 comparison, independent of the B.1 corrections.

This is presented in the source reports as intentional methodological
progress, not an unresolved conflict — but a reader of only `SUMMARY.md`
would come away with numbers that later reports explicitly retract.
