## [DC-1] Same-region suppression: an 8-slot history of enqueued regions. CONFIRMED (the E3a "last region only" rule is gone)
- `H:165` `#define SPECASYNC_REGION_HISTORY 8` (power of two, `static_assert` at `F:512-514`); storage `g_specasync_last_regions[8]`, `g_specasync_last_region_idx` (`H:168-169`, defined `D:157-159`), cleared by `specasync_clear` (`D:514-522`).
- Rule, in the per-fault hook loop (`F:2776-2808`): at **W > 1**, policy **first-touch**, and a non-zero predicted address, the region id is `_rid = _spec_addr >> (PAGE_SHIFT + log2 W)`. If `_rid` equals **any** of the 8 slots, the prediction is **not enqueued** and `ft_same_region` is incremented (`F:2791-2799`). Otherwise it is enqueued, and **only if `specasync_enqueue` returned true** the id is written into the slot at the round-robin index, which then advances modulo 8 (`F:2800-2807`).
- Consequences the text should respect: (i) at **W = 1 there is no suppression** (`else` branch, `F:2808-2810`; "every new code path is bypassed"); (ii) the history is **global** (not per VA space or per GPU); (iii) it holds the last **8 enqueued** regions, so a prediction dropped at a full queue does not enter it; (iv) replacement is FIFO by enqueue order, not LRU; (v) a region is a **W-aligned region of the address space** (`va >> (12 + log2 W)`), which equals the worker's staging region because blocks are 2 MB aligned.
- Section IV (line ~129): "a prediction whose region was already enqueued recently is not enqueued again". **Correct, but vague.** Proposed wording: "At $W>1$, a prediction is not enqueued if its $W$-page region is the same as that of any of the last eight enqueued predictions; one item then covers a region rather than one item per page of it. At $W=1$ no prediction is suppressed."

## [DC-2] `ft_fast`. Mostly CONFIRMED; two wording fixes
- **What the "ranges" are.** Maximal runs of **consecutive 4 KB pages in the page-sorted first-touch table** (`D:285-288`, build `D:866-882`): each range is `{base_pfn, len, off}`, `off` indexing a rank array so `g_ft_range_ranks[i] == g_ft_sorted[i].rank`. They are runs of the *table*, not allocations. Stencil-24K has **2** and GraphBFS-23 **19** (`ft_fast_nranges` in `e4_runs.csv`: stencil 2, graphbfs 19, 60 fast=1 rows each).
- **Rank.** `specasync_ft_fast_rank` (`D:779-829`): at **<= 16 ranges** (`SPECASYNC_FT_FAST_LINEAR_MAX`, `D:292`) a linear scan, otherwise a binary search over `base_pfn`; then `rank = ranks[off + (pfn - base)]` with explicit bounds checks. So "computed in constant time" is accurate for these workloads (2 and 19 ranges; the 19-range case uses the binary search over 19 entries) and **O(log ranges)** in general, not strictly constant. Proposed: "in time that depends only on the number of address runs (two for Stencil-24K, nineteen for GraphBFS-23), not on the number of table entries".
- **Cursor without a lock.** `specasync_ft_predict_fast` (`D:1075-1144`): reads the cursor atomically, recomputes skip / predict / held / exhausted from the observed value, and commits with **`atomic_try_cmpxchg`** on the same `atomic_t` cursor (`D:1097-1116`), retrying on contention with the value reloaded. **Bounded: `SPECASYNC_FT_FAST_MAX_TRIES = 64`** (`D:293`). After 64 failed commits it returns 0 (no prediction, cursor unchanged) and increments **`ft_fast_cas_giveup`** (`D:1120-1123`); that counter is in identity I1. By design it can only fire under a second concurrent cursor writer; the comment (`D:1065-1069`) says the single servicing thread per GPU provides none. **Reported value: `ft_fast_cas_giveup` = 0 on all 160 + 30 + 40 + 20 policy-6 rows of E4-E7** (`identity_check.csv`; I1 includes it, so any nonzero value would have appeared as a difference).
- **Load-time verification.** `specasync_ft_fast_build_and_verify` (`D:831-935`, called from the table load at `D:1035`): refuses unaligned or duplicate table pages; looks up **every table page** with both the range index and the original `bsearch` and requires identical ranks (`D:884-898`); and probes the page just below and just above every range, which must be unknown to both (`D:900-925`). Only then `ft_fast_verified = 1` and `g_ft_fast_active` is set with `smp_store_release` (`D:927-929`).
- **If verification fails** (also if allocation fails, or the table has an unaligned or duplicate page): `pr_err` names the first mismatch, the index is freed (`specasync_ft_fast_free`, `D:760`), `ft_fast_verified` stays 0, and **the module still loads and silently uses the original slow path** (`specasync_ft_predict`, `D:1147-1158`: the fast path is taken only if `g_ft_fast_active`). **The load is not refused.** The refusal is in the harness: `tests/e4_runner.py:18-19` stops the sweep with "ft_fast_verified != 1 on a fast = 1 load" (E5-E7 reuse it). Section IV's "every measured run with the fast lookup requires it to have passed" is therefore true **as a protocol rule enforced by the runner**, not by the module.
- Proposed wording for the last two sentences of "The lookup must be cheap": "At load time the module checks the fast lookup against the original for every table entry, and for the pages adjacent to each address run, and exports whether the check passed. If it fails, the module still loads and falls back to the original lookup; our harness stops any run that expected the fast lookup but reads a failed check."
- Also in that paragraph: the original path takes the spinlock **only for pages in the table** (`D:1183-1199`; an unknown page returns before the lock at `D:1178`), not "for every coalesced fault".

## [DC-3] Table collection. CONFIRMED, with one omission in Section IV
- ASLR off: the collector runs the benchmark as `timeout T setarch -R <bench>` (`tests/e09b_collect_tables.py:43`; the runners use the same, e.g. `e3b_runner.py:140`).
- Once per **coalesced** fault since E0.5: a **separate loop** over `batch_context->ordered_fault_cache[0 .. num_coalesced_faults-1]` calls `specasync_trace_push(fault_address)` (`F:2817-2866`), gated by `specasync_trace_faults` only (not by `specasync_log_enabled`), with the same per-entry skip condition as the prediction loop (`F:2767` vs `F:2864`), so trace[k] is the k-th coalesced fault on both the recording and consuming sides. Before E0.5 the push sat inside the per-dispatch-group loop (the 11.7x / 2.1x mismatch recorded in the code comment).
- **Omission:** the collection module is loaded with **the stock prefetcher disabled** (`uvm_perf_prefetch_enable=0`), `specasync_policy=0`, `specasync_log_enabled=0`, `specasync_trace_faults=1` (`e09b_collect_tables.py:33-36`). The table is therefore the first-touch order **with the prefetcher off**, and it is used unchanged in arms with the prefetcher on (C7), where prefetched pages never fault. Section IV should say so. Proposed: "In a collection run with address-space randomisation and the stock prefetcher disabled, the driver records ...".
- The first-touch reduction is `tests/prepare_first_touch_table.py` (not re-read here).

## [DC-4] Depth. CONFIRMED, with a precision on what "lookup" means
- `specasync_offload_depth` (`D:45`, default 0). In `specasync_worker_fn`: **depth >= 1 and a GPU reference** -> `uvm_va_block_make_resident(..., item->gpu->id, sregion, &pmask, NULL, UVM_MAKE_RESIDENT_CAUSE_PREFETCH)` (`F:394-399`). **depth 0** -> `uvm_va_space_up_read` and a **metadata-only** step: the block found by `uvm_va_block_find` (`F:343`) is only recorded in the hit table, result `HIT`/`MISS` (`F:429-441`); no `make_resident`, and at depth 0 no GPU reference is taken (`F:490-492`, `item->gpu` is NULL).
- "Lookup" in Section IV's sentence ("depth 0 performs the lookup without migrating") can be read as the oracle's table lookup, which happens on the **servicing thread** at both depths. It means the worker's block lookup. Proposed: "depth 0 has the worker find the block and record the prediction without migrating, and depth 1 also calls `make_resident`".
